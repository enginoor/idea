## What this product is

Name: OriginCheck. A native macOS app that answers one question: was this text or file generated by Claude?

It works through two technically opposite signals:

1. Text watermark analysis. Claude models launched on or after August 2, 2026 embed an invisible statistical watermark in generated prose. It travels with copy and paste, it survives light editing, and short or heavily edited passages carry no reliable signal. Anthropic has announced a detection API but has not released it, so the text side is a pluggable provider interface that reports the honest unavailable state until then.
2. C2PA metadata verification. Claude attaches signed provenance metadata to generated files such as png, jpg, and svg. This side works today, is cryptographically verifiable, and is the product's core credibility.

The repo is enginoor/idea. The owner's spec is complete and detailed; this file distills the thinking behind it so future sessions do not need to reread the whole document.

## The core asymmetry

A positive signal exists; a negative signal does not. A valid Claude-signed manifest is strong evidence the file was processed by Claude. The absence of a manifest proves nothing, because any re-save, conversion, screenshot, or upload pipeline can strip it. The same is true for the watermark: no mark can mean edited, paraphrased, translated, short, or generated by an older model.

The whole product follows from that: every verdict carries a caveat, every verdict carries evidence, and no negative result is ever presented as proof of human authorship.

## Product principles

1. Be the honest detector. Confidence is a range, not a verdict. Every screen educates, never accuses.
2. Positives are claims, not judgments. A detected mark means Claude likely processed the content. It does not prove AI authorship, plagiarism, or dishonesty.
3. Unknowns reduce confidence, never increase it. Unknown signer, expired certificate, missing metadata, short text: each pushes toward inconclusive.
4. The engine is the product. It is a pure Swift library with no UI imports, unit tested in CI, and treated like a library even inside the app.
5. Local and private by default. No telemetry, no accounts, no cloud. Raw content is stored only with explicit per-record consent; by default only a SHA-256 hash is kept.
6. No circumvention. No watermark removal, no detection-dodging advice. Ever.
7. Use the reference tooling. C2PA verification is done by c2patool, not reimplemented. The product's value is the UX and honest framing around verification, not the verification itself.
8. No overclaiming in marketing. The file side is real today; the text side is advertised as coming.

## Architecture

The engine (`Sources/OriginCheckEngine`) has no SwiftUI imports. Layers depend downward only:

- Models: `VerdictKind`, `Confidence`, `EvidenceItem`, `TextVerdict`, `FileVerdict`, `C2PAClaim`, `HistoryRecord`, `AnalysisOptions`, `ThresholdPreset`.
- `C2PAVerifier`: runs `c2patool` (path injectable), parses the manifest JSON leniently, maps to a `FileVerdict`. Unparseable output is reported as no manifest, never as a verdict on authorship.
- `MediaFormat`: the list of file formats c2patool can verify today, with case-insensitive extension parsing and display names. Covers images (png, jpg, jpeg, svg, webp, avif, heic, heif, tif, tiff, dng), video (mp4, mov), audio (m4a, mp3, wav), and pdf (read-only).
- `FolderVerifier`: scans a folder recursively, verifies every supported file with `C2PAVerifier`, and returns a `BatchReport` (summary counts, per-file verdicts, failures). One broken file does not stop the scan; hidden files and unsupported extensions are skipped. `toolMissing` flags the case where c2patool cannot be launched.
- `TextWatermarkAnalyzer`: `TextWatermarkProvider` protocol, `LocalStatisticalAnalyzer` (honest unavailable), `AnthropicDetectionAPIProvider` (scaffolded, feature flagged, Keychain key via `KeyStoring`).
- `VerdictCombiner`: merges provider results. A positive signal beats a negative one and the conflict is shown; short text caps confidence; all-unavailable reports notAvailable.
- `HistoryStore`: `HistoryStoring` protocol, `JSONHistoryStore` actor, `HistoryRecorder` with hash-only defaults.
- `SHA256`: dependency-free, tested against known vectors.

The app (`App/`) is a macOS-only SwiftUI package: Check tab (paste text or drop a file), History tab (search, export JSON, delete), Settings tab (providers, thresholds, retention, Keychain key), and a menu bar extra with clipboard check.

## Known tradeoffs and open items

- The text detection API does not exist yet. The honest unavailable state is the product until Anthropic ships it.
- File verification depends on c2patool being installed. Ship instructions and consider vendoring it.
- History is JSON, not SQLite. Acceptable for the MVP; swap to GRDB or SwiftData when volume demands it.
- The app target is compiled on macOS by GitHub Actions CI on every push, and by the release workflow in release mode. The development sandbox is Linux, so CI is the real compile gate. The app is ad-hoc signed by the packaging script but not yet sandboxed or notarized; both need a developer certificate or the owner's Mac.
- The manifest parser uses heuristic mapping for signature validity and modification state. It is tested against the fixtures and documented; real-world c2patool output should be fed back into the fixture library as it appears.

## Roadmap, in priority order

1. Build the app on a Mac, fix whatever Xcode surfaces, sandbox and notarize. Done through CI: the app compiles on macOS runners on every push and in the release pipeline. Sandboxing and notarization remain open and need an Apple Developer certificate.
2. Real Anthropic detection API integration the moment it ships, behind the existing provider interface.
3. Expand file formats: done at the engine level (full c2patool list). The app surfaces webp, pdf, mp4, and mov; the remaining formats can be added to the file importer when the app is built on a Mac.
4. Batch folder verification: engine done and tested. Remaining work is Mac-side only: build the report card UI and decide whether batches write to history (currently they do not; a batch has no single verdict kind).
5. SQLite-backed history.
6. Multi-model support later; the provider architecture already isolates model-specific logic.

## Working notes for future sessions

- Engine tests: `swift test` (works on Linux and macOS). The sandbox has Swift at /opt/swift/usr/bin; add it to PATH if it is not there.
- CI/CD: workflows live in `.github/workflows/`. `ci.yml` tests on every push; `release.yml` builds and publishes on `v*` tags and via workflow_dispatch. Packaging and notes are `Scripts/package-app.sh` and `Scripts/release-notes.sh`. Releases are ad-hoc signed, not notarized.
- Release process verified end to end: v0.1.0 is published with a zipped OriginCheck.app, a SHA-256 checksum in the notes, and the structured template. Future releases: tag vX.Y.Z and push; the pipeline gates on tests, builds, packages, and publishes.
- Swift 6 gotcha in the app: `Task {}` does not inherit MainActor isolation, and observable app state must be `@MainActor` or every capture into a Task is a data-race error. Follow the existing patterns in CheckView and MenuBar when adding async UI work.
- SwiftPM gotcha: the app package references the engine by path, and path dependencies are identified by the checkout folder name, not the manifest name. The repo folder is `idea`, so `App/Package.swift` uses `package: "idea"`. Renaming the checkout folder breaks the build; CI checks out into the repo name so it always matches.
- The platform's web checks do not apply to this repo anymore. The engine test suite is the verification gate.
